# CLAUDE.md — 팀 지식창고(wiki) 문서화 규칙

> 이 파일은 **Claude가 `wiki/` 안에서 문서를 만들 때 반드시 따르는 규칙**입니다.
> 사람이 아니라 LLM이 읽고 교차 참조하는 문서를 만드는 것이 목표입니다.
> "기억보다 기록을 (Memory fades. Write it down.)"

---

## 0. 이 폴더는 무엇인가

MarketON(dongnemarket) 레포 안에 사는 **LLM 위키**입니다. 팀원이 기능/버그/이슈
작업을 마칠 때마다 여기에 문서를 쌓고, 팀장은 나중에 Claude에게 자연어로 질문해
빠르게 파악합니다. 모든 문서는 **일관된 형식**이어야 합니다 — 형식이 흔들리면 교차
참조가 깨지고 검색이 느려집니다. 아래 규칙을 예외 없이 지키세요.

### 모듈 문서와의 경계 (중요)

이 리포의 기술 문서는 **설명하는 코드 옆에** 삽니다(`backend/backend.md`, `frontend/frontend.md`,
`infra/infra.md` …). 중앙 집중 `docs/` 폴더는 드리프트로 폐기했습니다. 역할이 다릅니다.

| | 성격 | 담는 것 |
|---|---|---|
| `<모듈>/<모듈>.md` | **현재 상태(spec)** — 항상 최신 | 지금 시스템이 *어떻게 생겼나* (구조·실행·테스트) |
| `wiki/` | **서사(narrative)** — 시점에 박제 | 이 작업을 *왜·어떻게 했고 뭐가 안 됐나* (실패 포함) |

핵심 차이는 **시제**입니다. 모듈 문서는 현재형이라 코드가 바뀌면 함께 고쳐야 하고,
wiki는 과거형이라 한번 쓰면 고치지 않습니다.

- 코드 구조·실행 절차가 바뀌면 그 갱신은 **모듈 문서**에서, 같은 PR로.
- **기술 결정(왜 이걸 골랐나)은 `wiki/decisions/`에 남깁니다.** 코드에서 복원되지 않는
  유일한 정보이므로 생략하지 마세요.
- API 요청/응답 스키마의 정본은 **Swagger**입니다. 어느 문서에도 옮겨 적지 않습니다.

## 1. 문서를 만들기 전에 반드시 확인할 것

1. 관련 GitHub PR/이슈 번호 (모르면 물어보세요)
2. 최근 커밋/브랜치 diff (어떤 파일이 바뀌었는지 — `gh pr view <n> --json files`)
3. 이 작업이 기존 문서와 연결되는지 (`features/`, `bugs/`를 훑어 `related`에 넣을 것)

정보가 부족하면 **추측하지 말고 사용자에게 한 가지만 질문**하세요.

---

## 2. 파일 위치와 이름 규칙

| 종류 | 폴더 | 파일명 형식 | 예시 |
|------|------|------------|------|
| 기능 추가 | `features/` | `FEAT-###-짧은설명.md` | `FEAT-204-redis-auth-ttl.md` |
| 버그 수정 | `bugs/` | `BUG-###-증상.md` | `BUG-207-admin-ai-dev-latency.md` |
| 논의/이슈 | `issues/` | `ISSUE-###-주제.md` | `ISSUE-012-검색성능.md` |
| 기술 결정 | `decisions/` | `ADR-###-결정내용.md` | `ADR-001-flyway-migration.md` |
| 주간 로그 | `weekly/` | `YYYY-Www.md` | `2026-W28.md` |

- **`###`(문서 번호)는 GitHub PR 번호와 1:1로 맞춥니다.** (이 팀은 PR 중심으로
  협업하므로 PR 번호를 기준으로 삼습니다. 이슈 번호가 따로 있으면 프론트매터에 함께 남기세요.)
  이게 "204번 PR 문서 찾아줘"를 가능하게 하는 핵심입니다.
- 설명은 짧게. kebab-case(영문) 또는 붙여쓴 한글 — 한 레포 안에서 일관되게.

## 3. 프론트매터 (가장 중요 — 절대 생략 금지)

모든 문서는 아래 YAML 프론트매터로 시작합니다. 쿼리 속도가 여기서 결정됩니다.

```yaml
---
id: FEAT-204
type: feature          # feature | bug | issue | decision
status: done           # todo | in-progress | done | wontfix
author: horangnabi97
date: 2026-07-09
related: [BUG-207]      # 관련 문서 id 배열, 없으면 []
tags: [인증, redis, 보안] # 검색용 키워드 3~6개
pr: 204                # 관련 PR 번호, 없으면 생략
---
```

규칙:
- `related`는 **실제로 존재하는 문서 id만** 넣습니다. 없는 id를 지어내지 마세요.
- `tags`는 도메인 용어 위주(예: 인증, 게시글, 채팅, 관리자AI, 알림)로 3~6개.
- `status`는 정확히 위 값 중 하나만.

## 4. 본문 섹션 구조

프론트매터 아래 본문은 문서 종류에 맞는 템플릿(`*/TEMPLATE.md`)을 그대로 따릅니다.
섹션 제목(`##`)을 임의로 바꾸거나 지우지 마세요. 내용이 없으면 `- 해당 없음`이라고 씁니다.

## 5. 글쓰기 톤

- **간결하게.** 사람 감동시키는 문장이 아니라, 6개월 뒤의 나와 Claude가 빠르게 이해할 글.
- 결론 먼저, 배경은 뒤에.
- "건드린 파일" 섹션에는 **실제 경로**를 씁니다 (`backend/src/main/java/com/dongnemarket/...`).
- 코드 스니펫은 이해에 꼭 필요한 부분만. 전체 붙여넣기 금지 (그건 코드가 하는 일).
- 실패한 시도도 반드시 기록합니다. "안 됐음"이 아니라 **왜 안 됐고 다음에 뭘 시도할지**.

---

## 6. 작업이 끝난 뒤

1. 문서를 알맞은 폴더에 생성
2. `related`가 있으면 **상대 문서의 `related`에도 역방향으로 추가**해 링크를 양방향으로
3. 커밋 메시지: `docs(wiki): FEAT-204 Redis 인증 TTL 문서 추가`
4. 해당 주의 `weekly/` 로그에 한 줄 요약 추가

---

## 7. 팀장 쿼리에 답할 때

- 먼저 프론트매터의 `type`/`status`/`tags`로 후보를 좁히고
- 여러 문서를 아우르는 질문이면 **문서별로 출처(id)를 밝히며** 요약
- 원문을 통째로 복붙하지 말고 **핵심만 재구성**
- 확실하지 않으면 "해당 문서에 정보 없음"이라고 정직하게 답하기

- 파일명 규칙 무시 ❌
