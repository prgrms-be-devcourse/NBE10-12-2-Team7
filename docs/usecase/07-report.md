# Report 유즈케이스 (UC-023 ~ UC-025) — 담당: 서유진

⚠️ 신규 신고는 항상 status=RECEIVED. 삭제(soft) 상품·탈퇴 회원도 신고 대상이 될 수 있음(테스트 전략 §8 갭).

---

# UC-023. 상품 신고

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-023 |
| 유즈케이스명 | 상품 신고 |
| Actor | 일반회원 (USER) |
| 목적 | 부적절한 상품을 신고한다 |
| 사전 조건 | 인증됨, 대상 상품 존재, 본인 상품 아님, 중복 아님 |
| 성공 결과 | 신고 생성(type=PRODUCT, status=RECEIVED) |
| 실패 결과 | 신고자 없음/상품 없음/본인 상품/중복/검증 실패 시 거부 |
| 우선순위 | Medium |
| 담당자 | 서유진 |

## 2. 기본 흐름

1. USER가 상품에 사유·내용을 입력해 신고한다.
2. 시스템이 사유 필수·내용 길이를 검증한다.
3. 신고자 존재를 확인한다.
4. 대상 상품을 조회한다.
5. 본인 상품 여부를 검사한다.
6. 동일 상품 중복 신고를 검사한다.
7. 신고를 저장한다(RECEIVED).
8. 결과를 반환한다(201).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 사유 null | 400 `COMMON_002` (@NotNull) |
| E-002 | 내용 501자 | 400 `COMMON_002` (@Size 500) |
| E-003 | 신고자 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-004 | 대상 상품 없음 | 404 `PRODUCT_NOT_FOUND` |
| E-005 | 본인이 등록한 상품 | 400 `REPORT_002 CANNOT_REPORT_OWN_PRODUCT` |
| E-006 | 이미 신고한 상품 | 409 `REPORT_005 DUPLICATE_REPORT` |

## 4. 비즈니스 규칙

- **검사 순서**: 신고자 존재 → 상품 존재 → 본인 상품 금지 → 중복 금지. (본인 상품+중복이면 `CANNOT_REPORT_OWN_PRODUCT` 우선)
- 사유(`ReportReason`)는 필수 enum, 내용은 선택(≤500자).
- 동일 (신고자, 상품) 중복 신고 불가.

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| reporterId | 신고자 (토큰) |
| productId | 대상 상품 |
| reason | 신고 사유 (enum, 필수) |
| content | 상세 내용 (선택, ≤500) |

## 6. 변경되는 데이터

| 데이터 | 변경 내용 |
| --- | --- |
| reports | 신규 row insert (type=PRODUCT, status=RECEIVED) |

## 7. API 후보

| Method | URL | 설명 |
| --- | --- | --- |
| POST | /api/products/{productId}/reports | 상품 신고 (인증) |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | 첫 신고 → type=PRODUCT, RECEIVED | RP-01, RP-10 |
| 실패 | 신고자/상품 없음, 본인 상품, 중복, 순서 | RP-02~RP-06 |
| 실패(엣지) | 사유 null/내용 501자/내용 null 허용 | RP-07~RP-09 |

# UC-024. 회원 신고

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-024 |
| 유즈케이스명 | 회원 신고 |
| Actor | 일반회원 (USER) |
| 목적 | 부적절한 회원을 신고한다 |
| 사전 조건 | 인증됨, 대상 회원 존재, 자기 자신 아님, 중복 아님 |
| 성공 결과 | 신고 생성(type=MEMBER, status=RECEIVED) |
| 실패 결과 | 신고자 없음/자기 신고/대상 없음/중복/검증 실패 시 거부 |
| 우선순위 | Medium |
| 담당자 | 서유진 |

## 2. 기본 흐름

1. USER가 회원에 사유·내용을 입력해 신고한다.
2. 시스템이 사유 필수·내용 길이를 검증한다.
3. 신고자 존재를 확인한다.
4. 자기 자신 신고 여부를 검사한다.
5. 대상 회원 존재를 확인한다.
6. 동일 회원 중복 신고를 검사한다.
7. 신고를 저장한다(RECEIVED).
8. 결과를 반환한다(201).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 사유 null | 400 `COMMON_002` |
| E-002 | 신고자 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-003 | 자기 자신 신고 | 400 `REPORT_003 CANNOT_REPORT_SELF` |
| E-004 | 대상 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-005 | 이미 신고한 회원 | 409 `DUPLICATE_REPORT` |

## 4. 비즈니스 규칙

- **검사 순서**: 신고자 존재 → 자기 신고 금지 → 대상 존재 → 중복 금지. (자기 자신이면 대상 조회 전에 `CANNOT_REPORT_SELF`)
- 동일 (신고자, 대상회원) 중복 신고 불가.

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| reporterId | 신고자 (토큰) |
| memberId | 대상 회원 |
| reason | 사유 (필수) |
| content | 내용 (선택, ≤500) |

## 6. 변경되는 데이터

| 데이터 | 변경 내용 |
| --- | --- |
| reports | 신규 row insert (type=MEMBER, status=RECEIVED) |

## 7. API 후보

| Method | URL | 설명 |
| --- | --- | --- |
| POST | /api/members/{memberId}/reports | 회원 신고 (인증) |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | 첫 신고 → type=MEMBER, RECEIVED | RP-20, RP-27 |
| 실패 | 신고자 없음/자기 신고/대상 없음/중복, 순서 | RP-21~RP-25 |
| 실패(엣지) | 사유 null | RP-26 |

# UC-025. 내 신고내역 조회

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-025 |
| 유즈케이스명 | 내 신고내역 조회 |
| Actor | 일반회원 (USER) |
| 목적 | 본인이 작성한 신고 목록을 조회한다 |
| 사전 조건 | 인증됨 |
| 성공 결과 | 본인 신고 목록(상품·회원·상태 무관 전체) |
| 실패 결과 | 신고자 없음 시 거부 |
| 우선순위 | Low |
| 담당자 | 서유진 |

## 2. 기본 흐름

1. USER가 내 신고내역을 요청한다.
2. 시스템이 신고자 존재를 확인한다.
3. 신고자의 모든 신고를 조회한다.
4. 목록을 반환한다(200).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 신고자 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-002 | 신고 이력 없음 | 빈 리스트 |

## 4. 비즈니스 규칙

- 본인 신고만 조회(상품/회원 신고 및 모든 상태 포함).

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |

## 6. 변경되는 데이터
