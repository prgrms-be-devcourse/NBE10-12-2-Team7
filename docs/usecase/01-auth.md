# Auth 유즈케이스 (UC-001 ~ UC-002) — 담당: 김대연

# UC-001. 회원가입

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-001 |
| 유즈케이스명 | 회원가입 |
| Actor | 비회원 (Guest) |
| 목적 | 이메일·비밀번호·닉네임으로 일반회원 계정을 생성한다 |
| 사전 조건 | 없음 (비인증 허용) |
| 성공 결과 | `ROLE_USER`·`ACTIVE` 회원 생성, 비밀번호는 BCrypt 인코딩되어 저장, 가입 정보 반환 |
| 실패 결과 | 이메일/닉네임 중복 또는 입력값 검증 실패 시 가입 거부 |
| 우선순위 | High |
| 담당자 | 김대연 |

## 2. 기본 흐름

1. Guest가 이메일·비밀번호·닉네임을 입력해 회원가입을 요청한다.
2. 시스템은 입력값 형식을 검증한다(이메일 형식, 비번 8~20자, 닉네임 2~20자).
3. 이메일 중복 여부를 확인한다.
4. 닉네임 중복 여부를 확인한다.
5. 비밀번호를 BCrypt로 인코딩한다.
6. `ROLE_USER`·`ACTIVE` 회원을 저장한다.
7. 가입 결과(SignupResponse)를 반환한다(201).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 입력값 형식 위반(이메일 형식/비번·닉네임 길이) | 400 `COMMON_002`, 첫 번째 필드 메시지 |
| E-002 | 이메일 중복 | 400대 409 `AUTH_001 DUPLICATE_EMAIL` |
| E-003 | 닉네임 중복 | 409 `AUTH_002 DUPLICATE_NICKNAME` |
| E-004 | 사전 중복체크 통과 후 저장 시점 UNIQUE 위반(race) | 원인 재조회 → 이메일이면 `DUPLICATE_EMAIL`, 닉네임이면 `DUPLICATE_NICKNAME`, 둘 다 정상이면 예외 재전파 |

## 4. 비즈니스 규칙

- 이메일·닉네임은 시스템 전체에서 유일하다.
- 신규 가입자는 항상 `ROLE_USER`·`ACTIVE`로 생성된다(관리자 가입 경로 없음).
- 비밀번호는 평문 저장 금지, BCrypt 인코딩 필수.
- 중복 검증은 애플리케이션 사전 검사 + DB UNIQUE 제약 이중 방어.

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| email | 가입 이메일 (형식 검증, 유일) |
| password | 평문 비밀번호 (8~20자) |
| nickname | 닉네임 (2~20자, 유일) |

## 6. 변경되는 데이터

| 데이터 | 변경 내용 |
| --- | --- |
| members | 신규 row insert (role=ROLE_USER, status=ACTIVE, password=인코딩값, createdAt 기록) |

## 7. API 후보

| Method | URL | 설명 |
| --- | --- | --- |
| POST | /api/auth/signup | 회원가입 (비인증) |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | 신규 이메일·닉네임 가입 → ROLE_USER·ACTIVE, 비번 인코딩 확인 | AU-01, AU-07, AU-11 |
| 실패 | 이메일/닉네임 중복 거부 | AU-02, AU-03 |
| 실패(엣지) | 비번 7자/21자·닉네임 1자/21자·이메일 형식오류 등 경계·방어 | AU-08~AU-10 |
| 실패(동시성) | save 시 UNIQUE 위반 → 원인별 변환/재전파 | AU-04~AU-06 |

# UC-002. 로그인

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-002 |
| 유즈케이스명 | 로그인 |
| Actor | 비회원 (Guest) |
| 목적 | 자격 증명을 검증하고 액세스 토큰(JWT)을 발급한다 |
| 사전 조건 | 가입된 ACTIVE 회원이 존재 |
| 성공 결과 | JWT 액세스 토큰 발급(subject=memberId, role 클레임 포함) |
| 실패 결과 | 미존재/정지/탈퇴/비번불일치 시 로그인 거부 |
| 우선순위 | High |
| 담당자 | 김대연 |

## 2. 기본 흐름

1. Guest가 이메일·비밀번호로 로그인을 요청한다.
2. 시스템은 입력값 형식을 검증한다(필수값).
3. 이메일로 회원을 조회한다.
4. 회원 상태를 검사한다(DELETED → SUSPENDED 순).
5. 비밀번호 일치 여부를 검증한다.
6. memberId·role로 JWT 액세스 토큰을 발급한다.
7. 토큰(LoginResponse)을 반환한다(200).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 이메일/비번 미입력 | 400 `COMMON_002` |
| E-002 | 이메일에 해당하는 회원 없음 | 404 `MEMBER_001 MEMBER_NOT_FOUND` |
| E-003 | 탈퇴 회원(DELETED) | 400 `MEMBER_002 DELETED_MEMBER` |
| E-004 | 정지 회원(SUSPENDED) | 403 `MEMBER_003 SUSPENDED_MEMBER` |
| E-005 | 비밀번호 불일치 | 401 `AUTH_003 INVALID_PASSWORD` |

## 4. 비즈니스 규칙

- **검증 순서**: 존재 → 상태(DELETED/SUSPENDED) → 비밀번호. 상태가 비밀번호보다 **먼저** 검사된다(탈퇴/정지 회원에게 비번 오류를 노출하지 않음).
- SUSPENDED/DELETED 회원은 로그인할 수 없다.
- 토큰 유효시간은 설정값(기본 3600초). Refresh 토큰 없음.

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| email | 로그인 이메일 |
| password | 평문 비밀번호 (저장된 BCrypt 해시와 비교) |

## 6. 변경되는 데이터

| --- | --- |
| (없음) | 상태 변경 없음. 토큰 발급만(서버 무상태) |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | ACTIVE·비번 일치 → 토큰 발급(인자 role 포함) | AU-20, AU-26, AU-27 |
| 실패 | 미존재/정지/탈퇴/비번불일치 각각 | AU-21~AU-24 |
