# Member 유즈케이스 (UC-003 ~ UC-005) — 담당: 김대연

공통 사전조건: 인증된 USER. principal = memberId. 세 UC 모두 `findById` → **활성회원 검사**(DELETED→`DELETED_MEMBER`, SUSPENDED→`SUSPENDED_MEMBER`) 선행.

---

# UC-003. 내 정보 조회

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-003 |
| 유즈케이스명 | 내 정보 조회 |
| Actor | 일반회원 (USER) |
| 목적 | 로그인한 본인의 프로필 정보를 조회한다 |
| 사전 조건 | 인증됨, 본인 계정이 ACTIVE |
| 성공 결과 | 본인 프로필(MemberResponse) 반환 |
| 실패 결과 | 회원 없음/정지/탈퇴 시 조회 거부 |
| 우선순위 | Medium |
| 담당자 | 김대연 |

## 2. 기본 흐름

1. USER가 본인 정보 조회를 요청한다(토큰의 memberId 사용).
2. 시스템이 memberId로 회원을 조회한다.
3. 활성 상태를 검사한다.
4. 프로필 정보를 반환한다(200).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 미인증 접근 | 401 `COMMON_003` |
| E-002 | memberId로 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-003 | 탈퇴 회원 | 400 `DELETED_MEMBER` |
| E-004 | 정지 회원 | 403 `SUSPENDED_MEMBER` |

## 4. 비즈니스 규칙

- 본인 정보만 조회 가능(타인 조회 엔드포인트 없음).
- 정지/탈퇴 회원은 자원 접근 불가.

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| memberId | 토큰 principal (조회 키) |

## 6. 변경되는 데이터

| 데이터 | 변경 내용 |
| --- | --- |
| (없음) | 조회 전용 |

## 7. API 후보

| Method | URL | 설명 |
| --- | --- | --- |
| GET | /api/members/me | 내 정보 조회 |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | ACTIVE 회원 조회 | ME-01 |
| 실패 | 회원 없음/정지/탈퇴 | ME-02~ME-04 |
| 실패(인가) | 비인증 401 | ME-30 |

# UC-004. 내 정보 수정

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-004 |
| 유즈케이스명 | 내 정보 수정 |
| Actor | 일반회원 (USER) |
| 목적 | 본인 닉네임을 변경한다 |
| 사전 조건 | 인증됨, 본인 ACTIVE |
| 성공 결과 | 닉네임 변경, 변경된 프로필 반환 |
| 실패 결과 | 회원 없음/정지/탈퇴/닉네임 중복/검증 실패 시 거부 |
| 우선순위 | Medium |
| 담당자 | 김대연 |

## 2. 기본 흐름

1. USER가 새 닉네임을 입력해 수정을 요청한다.
2. 시스템이 닉네임 형식을 검증한다(2~20자).
3. memberId로 회원을 조회하고 활성 상태를 검사한다.
4. 닉네임 중복을 검사한다(본인 제외).
5. 닉네임을 변경한다.
6. 변경된 프로필을 반환한다(200).

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 닉네임 공백/1자/21자 | 400 `COMMON_002` |
| E-002 | 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-003 | 정지/탈퇴 회원 | 403/400 `SUSPENDED_MEMBER`/`DELETED_MEMBER` |
| E-004 | 타인이 사용 중인 닉네임 | 409 `DUPLICATE_NICKNAME` |

## 4. 비즈니스 규칙

- 닉네임 중복 검사는 **본인 제외**(`existsByNicknameAndIdNot`) — 자기 현재 닉네임 재제출은 허용.
- 변경 가능 필드는 닉네임뿐(이메일·비밀번호·권한 변경 경로 없음).

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| memberId | 토큰 principal |
| nickname | 새 닉네임 (2~20자) |

## 6. 변경되는 데이터

| 데이터 | 변경 내용 |
| --- | --- |
| members.nickname | 새 값으로 갱신 (updatedAt 갱신) |

## 7. API 후보

| Method | URL | 설명 |
| --- | --- | --- |
| PATCH | /api/members/me | 내 정보 수정 |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | 새 닉네임 변경 / 본인 닉네임 그대로 재제출 허용 | ME-10, ME-14 |
| 실패 | 회원 없음/정지/탈퇴/타인 닉네임 중복 | ME-11~ME-13 |
| 실패(엣지) | 닉네임 길이 경계·공백 방어 | ME-15 |

# UC-005. 회원 탈퇴

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 유즈케이스 ID | UC-005 |
| 유즈케이스명 | 회원 탈퇴 |
| Actor | 일반회원 (USER) |
| 목적 | 본인 계정을 탈퇴(soft delete)한다 |
| 사전 조건 | 인증됨, 본인 ACTIVE |
| 성공 결과 | status=DELETED, deletedAt 기록 |
| 실패 결과 | 회원 없음/이미 탈퇴/정지 시 거부 |
| 우선순위 | Medium |
| 담당자 | 김대연 |

## 2. 기본 흐름

1. USER가 탈퇴를 요청한다.
2. 시스템이 memberId로 회원을 조회하고 활성 상태를 검사한다.
3. 회원을 soft delete 처리한다(status=DELETED, deletedAt=now).
4. 성공 응답을 반환한다.

## 3. 예외 흐름

| 번호 | 예외 상황 | 시스템 처리 |
| --- | --- | --- |
| E-001 | 회원 없음 | 404 `MEMBER_NOT_FOUND` |
| E-002 | 이미 탈퇴(DELETED) | 400 `DELETED_MEMBER` (재탈퇴 방지) |
| E-003 | 정지 회원 | 403 `SUSPENDED_MEMBER` |

## 4. 비즈니스 규칙

- 탈퇴는 물리 삭제가 아닌 soft delete(데이터 보존).
- 탈퇴 회원은 로그인 불가(UC-002 E-003).
- 탈퇴 시 작성한 상품/댓글/관심은 본 UC에서 연쇄 처리하지 않음(현재 구현).

## 5. 필요한 데이터 후보

| 데이터 | 설명 |
| --- | --- |
| memberId | 토큰 principal |

## 6. 변경되는 데이터

| 데이터 | 변경 내용 |
| --- | --- |
| members.status | DELETED |
| members.deletedAt | now() 기록 |

## 7. API 후보

| Method | URL | 설명 |
| --- | --- | --- |
| DELETE | /api/members/me | 회원 탈퇴 |

## 8. 테스트 관점

| 구분 | 테스트 내용 | 연계 |
| --- | --- | --- |
| 성공 | ACTIVE 회원 탈퇴 → DELETED·deletedAt 기록 | ME-20 |
| 실패 | 회원 없음/이미 탈퇴/정지 | ME-21~ME-23 |
