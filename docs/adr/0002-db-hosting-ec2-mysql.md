# 0002. 운영 DB를 EC2 자체 호스팅 MySQL로 운영

> 상태: Accepted · 날짜: 2026-07-07

## 배경 (Context)

클라우드 배포에서 데이터베이스를 어디에 둘지 결정이 필요했다. 후보는 관리형 **RDS**와 **EC2에 MySQL 컨테이너 직접 호스팅**.

## 결정 (Decision)

운영 DB를 **별도 DB EC2에 MySQL 8 컨테이너로 직접 호스팅**한다(관리형 RDS 미사용). 앱 EC2와 동일한 컨테이너 구성을 재사용해, 로컬/개발 배포와 운영의 DB 실행 방식을 일치시킨다.

- DB EC2는 **퍼블릭 IP 없이** 같은 VPC의 앱 EC2만 Security Group으로 3306 허용.
- 정의: [`infra/cloud/db/`](../../infra/cloud/db/).

## 결과 (Consequences)

**좋은 점**
- 로컬 docker-compose와 동일한 MySQL 컨테이너 구성 → 환경 간 차이 최소, 학습·재현 쉬움.
- 비용 통제와 구성 투명성(전부 compose로 노출).

**감수하는 비용 / 후속**
- 백업·장애복구·패치·모니터링을 **직접** 해야 한다(RDS의 자동 백업·Multi-AZ·자동 페일오버 없음).
- 데이터 내구성은 EC2 볼륨에 의존. 스냅샷·백업 정책을 별도로 세워야 한다(후속).
- 확장(수직/수평)·가용성 요구가 커지면 RDS 재검토. 전환 시 새 ADR로 이 결정을 supersede.

## 대안 (Alternatives)

- **관리형 RDS**: 백업·가용성·운영 부담이 크게 준다. 그러나 이번 범위(부트캠프 프로젝트)에선 비용·구성 단순성·환경 일치를 우선해 보류. 운영 성숙도가 올라가면 1순위 전환 후보.
