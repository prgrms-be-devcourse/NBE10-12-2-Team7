# 0001. docs를 Docs-as-Code 구조로 재편

> 상태: Accepted · 날짜: 2026-07-07

## 배경 (Context)

1차 프로젝트에서 `docs/`는 프로젝트 초기에 AI 에이전트로 빠르게 개발하려고 세팅한 문서(`docs/ai/`)와 API 테스트 문서(`docs/postman/`) 위주였다. 진행하면서 다음 문제가 드러났다.

- **문서가 코드 진행을 못 따라갔다.** 초기 기획 문서(`ai/`)는 그대로 굳었고, 실제 코드는 그 사이 `notification`·`chat`·`region`·`admin.ai` 도메인까지 늘었다. 문서와 코드가 어긋났다.
- **삭제 후 참조가 깨졌다.** 이전 정리에서 `architecture/`·`convention/`·`deployment/` 등을 지웠지만 README들은 여전히 삭제된 폴더를 가리켰다.
- **성격이 다른 것이 섞여 있었다.** 재사용용 부트스트랩 키트(`ai/`), 개인/비밀이 얽힌 테스트 자산(Postman), 팀 공유 기술 문서가 한 폴더에 공존했다.
- **어디에 무엇을 기록할지 규칙이 없었다.** 그래서 아무도 꾸준히 갱신하지 않았다.

2차 프로젝트에서는 문서 관리를 철저히 하기로 하고, 그 기준을 코드베이스와 함께 확정할 필요가 있었다.

## 결정 (Decision)

`docs/`는 **코드와 함께 버전 관리·리뷰되는 기술 문서만** 두는 Docs-as-Code 저장소로 재편한다. 판단 기준은 **"이 문서가 코드와 함께 바뀌어야 하나?"** — Yes면 `docs/`, No(프로세스·기획·회의록)면 Notion/위키.

구체적으로:

- **폴더 구조**를 `getting-started · architecture · adr · api · runbook · conventions` 로 고정하고, `docs/README.md`를 인덱스 겸 "무엇을 어디에 두나" 경계 문서로 둔다.
- **architecture**는 C4 모델(Context→Container→Component)+ERD로 작성하고, 코드를 정본으로 삼아 실측 반영한다.
- **결정은 ADR**(이 폴더)로 번호순 기록한다.
- **API 정본은 코드→Swagger/Springdoc**, Postman은 거기서 import하는 파생물로 취급한다.
- **성격이 다른 자산은 저장소 밖으로 분리**한다: 재사용 부트스트랩 키트와 Postman 컬렉션은 개인 아카이브로 뺐다.
- **동기화 규칙**: 코드가 바뀌면 관련 문서를 같은 PR에서 갱신한다.

## 결과 (Consequences)

**좋은 점**
- 문서와 코드가 같은 PR에서 함께 움직여, 어긋남이 줄어든다.
- 신규 투입자가 `docs/README.md` 하나에서 전체 지도를 얻는다.
- "왜 그렇게 했나"가 ADR로 남아 반복 논쟁이 준다.

**감수하는 비용 / 후속 작업**
- 빈 폴더(`getting-started`·`api`·`runbook`·`conventions`)는 아직 미작성 — 단계적으로 채운다. 그 전까지 인덱스에 `⬜ 예정`으로 표기.
- 문서를 PR에 포함하는 습관이 정착돼야 효과가 난다(규칙만으로는 부족, 리뷰에서 확인 필요).
- `api` 정본을 Swagger로 두려면 Springdoc 설정·`.env.example` 컨벤션 정비가 필요하다.

## 대안 (Alternatives)

- **전부 Notion/위키로**: 검색·공유는 편하나 코드와 버전이 따로 놀아 지금 문제(어긋남)를 못 고친다. 그래서 기각.
- **기존 `ai/`·`postman/` 유지·보수**: 성격이 섞여 있어 "무엇을 어디에" 기준이 안 서고, 초기 기획 문서라 as-built와 계속 어긋난다. 분리하는 편이 깔끔.
- **폴더 없이 평평하게 문서만 나열**: 규모가 커지면 종류(설명·참조·절차)가 섞여 지금과 같은 혼란이 재발. 목적별 폴더로 분리.
