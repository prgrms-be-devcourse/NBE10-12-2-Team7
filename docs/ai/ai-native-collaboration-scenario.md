# AI Native 협업과정 시나리오

`docs/ai/`의 문서들(00 공통 규칙, 01~05 도메인 에이전트)과 협업 규칙이 **실제로 어떻게 맞물려 돌아가는지**를 하루 일과로 정리한 시나리오다. 예시 기능은 권건우(Favorite)의 "관심 상품 등록"을 사용한다.

> 한 줄 요약: **00이 모두에게 같은 규칙을 학습시키고 → 역할 선택으로 01~05에 연결되어 각자 도메인만 개발하며 → 09:00~17:00 동안 PR이 올라올 때마다 팀장이 상시로 검수·통합한다.**

---

## 하루 일과 한눈에 보기

```
Day 0   팀장: 기본 환경 세팅 (global, ApiResponse, ErrorCode 골격, Security 등) → develop 고정

09:00 ~ 17:00  [상시 루프]
   팀원 │ 프로젝트 이해(00) → 역할 선택(01~05) → 5단계 흐름으로 기능 구현
        │ (① ErrorCode → ② 구현 → ③ 단위테스트 → ④ Postman) → ⑤ PR 요청
   팀장 │ PR이 올라올 때마다 별도 에이전트(06) 연결 → 코드 로직·구조 이해 → 검증·테스트
        │ → 문제 없으면 develop 통합 (PR마다 그때그때)

17:00 ~ 18:00  [마무리]
   팀원 │ 오늘 작업 내용 · 테스트 결과 · 내일 계획 문서 정리
   팀장 │ develop 한 번 더 코드 검증 → develop 최종 통합 상태 확정

마일스톤  팀장: develop → main
```

핵심: 통합은 **하루 끝에 몰아서가 아니라 09:00~17:00 내내 PR 단위로 상시** 일어난다. 그래서 develop이 늘 최신이고 충돌이 작다.

---

## Day 0 — 팀장(조민석)이 기본 환경을 먼저 세팅

팀장은 에이전트에게 `00-ai-common-rules.md`를 읽혀 역할 1(팀장/공통구조·Admin)을 선택하고, `05-admin-common-agent.md`로 넘어가 아래를 `develop`에 올려 고정한다.

```
global 골격(common·config·exception·response·security)
ApiResponse<T> / ErrorResponse
ErrorCode.java (COMMON + 도메인별 빈 주석 영역)
GlobalExceptionHandler / SecurityConfig(JWT) / build.gradle / application.yml / Swagger 설정
main·develop 브랜치 보호
```

**→ 이 베이스가 깔리기 전에는 누구도 도메인 PR을 올리지 않는다.** 모든 팀원이 같은 응답·예외 구조 위에서 출발하게 만드는 단계.

---

## 09:00~17:00 — 팀원 개발 + 팀장 상시 통합

### 팀원 (예: 권건우, "관심 상품 등록")

권건우는 에이전트에게 `00-ai-common-rules.md`를 먼저 읽힌다. 에이전트가 "어떤 역할을 맡으셨나요?"라고 물으면 **4번(Favorite·Comment)** 을 고른다. 에이전트는 `03-favorite-comment-agent.md`를 읽어 역할을 잡고 "어떤 기능부터 진행할까요?"라고 묻는다. 권건우가 "관심 상품 등록"이라 답하면, **5단계 흐름**으로 진행한다.

```
① ErrorCode 작성 — 예외 분석(비로그인 / 상품 없음 / 이미 관심 등록) 후 FAVORITE_ALREADY_EXISTS(409) 등 정의
② 기능 구현      — favorite 패키지만. 로직은 Service, favorites(member_id, product_id) UNIQUE, 성공은 ApiResponse<T>
③ 단위 테스트    — 성공 1 + 실패 2(상품 없음 404, 중복 409)
④ Postman 테스트 — 성공/실패 케이스 검증 + 시나리오 문서
⑤ PR 요청        — 직접 검토 후 feature/favorite_create → develop 로 작은 PR
```

권건우는 기능이 완성되는 대로 **바로 PR을 올린다**(하루치를 몰아두지 않는다). 같은 시간 김대연(auth)·한상민(product)·서유진(report)도 각자 도메인을 병렬로 개발하는데, 패키지 경계가 갈려 충돌이 거의 없다.

### 팀장 (PR이 올라올 때마다 상시 검수·통합)

권건우의 PR이 올라오면, 팀장은 **별도 에이전트(06 통합 도구)** 를 연결해 그 PR을 검수한다.

```
- 코드 로직·구조 이해: 변경 파일·diff 파악
- 검증: 담당 패키지만 수정했는가 / ApiResponse·BusinessException 적용 / 단위테스트·Postman 존재
- 테스트: 빌드·기동·핵심 동작 확인
- 판정: 통과면 develop 머지, 문제면 보류 사유와 함께 권건우에게 반려
```

이 검수·통합을 **PR이 들어올 때마다** 반복한다. 팀장은 같은 시간 admin 로직 설계도 병행하는데, admin은 팀원 개발이 어느 정도 된 뒤 만드는 후순위 기능이라 충돌이 없다. (PR 알림이 오면 리뷰를 우선한다.)

---

## 17:00~18:00 — 마무리

- **팀원**: 오늘 작업 내용, 테스트 결과, 발생한 문제, 내일 작업 계획을 Notion에 정리한다.
- **팀장**: develop 전체를 한 번 더 코드 검증하고, 정상 실행을 확인한 뒤 develop 최종 통합 상태를 확정한다. 깨지는 부분이 있으면 해당 PR 작성자와 함께 복구한다.

---

## 결과

`develop`은 하루 종일 상시 통합 덕분에 **항상 최신·실행 가능(green)** 상태를 유지하고, 각 기능은 단위 테스트·Postman 문서까지 갖춰 머지된다. 5명이 서로 다른 AI로 빠르게 개발해도, **공통 베이스 선고정 + 도메인 경계 + 5단계 흐름 + 상시 검수** 덕분에 구조가 무너지지 않는다. 발표/마일스톤 시점에만 팀장이 develop → main으로 올린다.
