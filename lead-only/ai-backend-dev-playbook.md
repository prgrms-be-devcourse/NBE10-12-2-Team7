# AI와 함께 백엔드 개발하기 — 설계 주도권을 잃지 않는 법

> 신입 백엔드 개발자가 AI의 속도를 누리되, **"왜 이렇게 설계하나 · 왜 이 기능인가 · 대안은 무엇인가"의 주도권을 본인이 쥐기 위한** 작업 방식 + 복붙용 프롬프트 모음.
> 작성 2026-06-30. 계기: admin 로직을 AI에 맡겨 설계 감각이 무뎌졌다는 자각 → 앞으로는 AI와 "같이 생각하며" 개발하기 위해.

---

## 0. 마음가짐 — 역할이 바뀐다

AI 시대에 개발자의 일은 **"코드를 타이핑하는 사람" → "결정하고 검증하는 사람"** 으로 옮겨간다.

- **AI = 빠른 구현자.** 너 = **의사결정자 · 아키텍트 · 리뷰어.**
- AI의 기본 출력은 **"동작하는 평범한 코드"**, 결코 **"네 맥락의 최선"**이 아니다. 맥락을 안 주면 일반론을, 안 물으면 침묵을 준다.
- 그래서 네 4가지 일: ① 결정을 **표면화**시키고 ② **대안·트레이드오프**를 요구하고 ③ 네 **맥락(제약)**을 주입하고 ④ **네가 재설명할 수 있을 때만** 통과시킨다.

> **황금률: "내가 말로 다시 설명하지 못하는 코드는 머지하지 않는다."**
> 이거 하나만 지켜도 AI 의존으로 인한 실력 저하의 90%를 막는다.

---

## 1. 개발 루프 (한 기능을 이 순서로)

```
① 맥락 제공  →  ② [코드 금지] 설계안 요구  →  ③ 대안·트레이드오프 심문
                                                      │
                          ⑦ 검수(실패모드·엣지)  ←  ⑥ 리뷰(결정 재진술)  ←  ⑤ 구현 요구  ←  ④ [내가] 결정
```

핵심은 **②~④** — 코드를 받기 전에 "어떻게·왜·대안"을 먼저 끝내는 것. 코드부터 받으면 이미 결정이 내려진 뒤라 되돌리기 어렵다.

## 2. 단계별 프롬프트 (복붙용)

### A. 구현 전 — 설계부터 (가장 중요)
```
[기능]을 구현하려고 해. 아직 코드는 쓰지 마.
먼저 이것부터 줘:
① 가능한 접근법 2~3개
② 각각의 트레이드오프(장점 / 단점 / 숨은 비용)
③ 네 추천 1개와 그 이유
④ 내가 결정해야 할 선택지(표로)
내 제약: [규모·트래픽 / 팀 수준 / 기존 스택·컨벤션 / 성능·보안·정합성 요구 / 마감]
```

### B. 결정 심문 (AI가 내린 선택을 캐묻기)
```
방금 이 부분 왜 이렇게 설계했어? 한 줄씩 답해:
- 어떤 문제를 풀려고?
- 고려한 대안은? 왜 그건 안 골랐어?
- 이 선택이 '틀린 선택'이 되는 조건은?
```

### C. 트레이드오프 강제 (장점만 말하는 AI 차단)
```
장점 말고. 이 설계의 단점·숨은 비용·한계와,
6개월 뒤 후회할 가능성이 있는 지점을 솔직하게.
운영에서 가장 먼저 터질 곳 순서로 적어줘.
```

### D. 맥락 주입 (매 요청 앞에 깔기)
```
답하기 전에 내 맥락을 전제로 해:
- 규모/트래픽: ...
- 팀 수준 / 유지보수 주체: ...
- 기존 스택·컨벤션: ... (예: Spring Boot 3.5, 계층형, ApiResponse 래퍼, BusinessException+ErrorCode)
- 성능 / 보안 / 정합성 요구: ...
- 마감 / 우선순위: ...
이 맥락에서 '과하지도 부족하지도 않은' 선택을 제안해.
```

### E. 구현 후 — 리뷰/검수
```
이 코드의 설계 결정들을 목록화해줘.
- 각 결정마다 '왜 그렇게 했는지' 한 줄.
- 일반 관습과 다르게 한 부분은 ⚠️ 표시.
- 이 코드가 깨지는 상황(실패 모드 · 동시성 · 잘못된 입력 · 데이터 폭증)을 따로.
```

### F. 학습 모드 (소크라테스 — 이번 admin 세션에서 쓴 그 방식)
```
이 코드를 나에게 소크라테스식으로 가르쳐줘. 규칙:
- 한 번에 질문 하나. 답을 먼저 주지 마.
- 내가 먼저 답하면, 맞은 점/놓친 점/더 깊은 이유를 '개념 이름'과 함께 피드백.
- 막히면 내가 '힌트 / 패스 / 더 쉽게' 요청할게.
코드 → 질문 → (내 답) → 피드백 순으로.
```

## 3. 백엔드 결정 체크리스트 (AI 코드를 받으면 이걸로 심문)

AI가 **조용히 넘어가는** 것들. 코드를 볼 때마다 스스로/AI에게 물어라.

| 축 | 핵심 질문 |
|---|---|
| **트랜잭션** | 경계가 맞나? 읽기는 readOnly인가? 여러 저장이 한 트랜잭션(원자적)인가? |
| **실패 모드** | 중간에 실패하면? 부분 실패 시 데이터 정합성은? |
| **동시성** | 두 요청이 동시에 같은 걸 바꾸면? 락이 필요한가(lost update)? |
| **데이터 규모** | 건수가 10만이면? N+1은? 페이징은? |
| **경계** | 엔티티를 그대로 밖으로 내보내나(민감정보 유출)? DTO 경계가 있나? |
| **검증 위치** | 어디서 검증하나? 비싼 작업(DB) 앞인가(fail-fast)? |
| **에러 일관성** | 에러 응답이 API 전체와 일관된가? 내가 통제하는가? |
| **보안** | 권한·인증 확인? 입력을 신뢰하나? |
| **관측가능성** | 무슨 일이 있었는지 남나(로그·감사)? 누가·언제 했나? |

> **연결:** 이번 admin 세션에서 네가 마주친 질문들이 **바로 이 체크리스트의 실제 적용**이었다.
> `readOnly` → 트랜잭션 · `DTO 변환` → 경계 · `parseStatus 순서` → 검증 위치(fail-fast) · `changeStatus` → 정합성/캡슐화.
> **내가 너에게 던진 질문 = 네가 AI에게 던져야 할 질문.**

## 4. 위험 신호 (이러면 멈춰라)

- 🚩 AI가 **질문 없이 큰 코드 덩어리**를 한 번에 던진다 → 검토 불가. 작게 쪼개서 다시.
- 🚩 결정 이유를 **안 물었더니 안 알려준다** → 기본값은 침묵이다. 네가 물어라(프롬프트 B).
- 🚩 **장점만** 나열한다 → 단점·비용을 강제로 요구(프롬프트 C).
- 🚩 "그냥 이게 표준이에요"로 넘어간다 → **네 맥락에서도 표준인지** 따로 확인.
- 🚩 동작은 하는데 **네가 재설명을 못 한다** → 머지 금지(황금률 위반).

---

## 5. 한 장 요약

> **AI에게 코드를 시키되, 결정은 네가 한다.**
> 1. 코드 전에 **설계·대안·트레이드오프**부터(②~④).
> 2. 매 요청에 **네 맥락(제약)**을 깔아라.
> 3. 모든 비자명한 선택에 **"왜? 대안은? 언제 틀려?"**.
> 4. **재설명 못 하면 머지하지 마라.**
> 5. 가끔은 **소크라테스 모드**로 스스로를 테스트해 감각을 유지하라.

---

## 6. 운영 모델 — AI를 '직원'처럼: 제안 → 승인 워크플로우

> 내가 원하는 방식: 요청을 던지면 AI가 알아서 **요구분석·설계·구현·테스트**까지 하되, 그 과정을 **팀장인 내가 이해하고 승인한 뒤에야** 기능이 들어가게 한다.
> **나 = 팀장(승인권자) · AI = 주니어 엔지니어.** 직원은 일을 다 해오되, **머지 전에 팀장을 설득**해야 한다.

별난 방식이 아니다. 좋은 팀이 주니어에게 큰 기능을 맡길 때 쓰는 **설계 문서(RFC) + 리뷰** 관행을 AI에 적용한 것. 덤으로, 제안서를 읽고 승인하는 과정에서 잃었던 설계 감각이 돌아온다.

### 단계와 승인 게이트 (stage-gate)
| 단계 | 직원(AI)이 하는 일 | 팀장(나)의 게이트 |
|---|---|---|
| 1. 요구사항 분석 | 문제·범위·비범위·전제 정리 | "푸는 문제가 이게 맞나?" |
| 2. **설계 제안(RFC)** | 접근법 후보 + 트레이드오프 + 추천·이유 + 영향범위 + 리스크 | **"이 설계로 가도 되나?" ← 설득당해야 진행** |
| 3. 구현 | 승인된 설계대로, 단위별 | "설계대로 됐나? 결정을 내가 재설명되나?" |
| 4. 테스트·검수 | 무엇을 어떻게 검증, 실패모드·엣지 | "믿고 머지 가능한가?" |

각 게이트에서 **승인 / 수정요청 / 반려.** 승인 전엔 다음 단계 금지.

### 기능 제안서(RFC) 템플릿 — 예: "OAuth 로그인 도입"
```
# 기능 제안서: OAuth(구글·카카오) 로그인 도입

## 1. 요구사항 분석
- 문제: 자체 가입/로그인만 있어 진입장벽↑. 소셜 로그인으로 가입 전환율↑
- 범위: 구글·카카오로 가입·로그인 + 기존 JWT 발급까지 연결
- 비범위(1차 제외): 기존 이메일계정과 소셜계정 '연동', 다중 소셜 병합
- 전제/제약: 기존 JWT 체계·Member 엔티티 재사용, Spring Boot 3.5

## 2. 설계 제안 (핵심)
| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | spring-security-oauth2-client | 표준·검증됨, 토큰교환 자동 | 설정 복잡, 학습곡선 |
| B | 직접 OAuth 호출(RestClient) | 흐름 투명, 통제력 | 직접구현 부담, 보안실수 위험 |
- 추천: **A** — 보안 민감 영역은 검증된 표준에 맡긴다(원칙)
- 영향범위: SecurityConfig 변경 · Member에 provider/providerId 필드 추가(→ 스키마 마이그레이션!) · 신규 OAuthSuccessHandler
- 리스크: 소셜 이메일 ↔ 기존 이메일 충돌 처리 / redirect URI 관리 / 최초 로그인 시 닉네임 정책

## 3. 구현 계획 (단위)
1) 의존성·설정 → 2) Member 확장 → 3) 성공 핸들러에서 JWT 발급 → 4) 테스트

## 4. 테스트 전략
- 신규 소셜 유저 가입 / 기존 이메일 충돌 / JWT 정상 발급 / 실패(인가 거부) 흐름

## 5. 팀장이 결정할 선택지
- [ ] 접근법 A로 진행 OK?
- [ ] 이메일 충돌 정책: 자동 연동 vs 에러 반환 — 어느 쪽?
- [ ] 1차 범위에서 카카오·구글 둘 다 vs 하나 먼저?
```
> 직원이 SWE 작업을 다 하되, **§5(결정할 선택지)** 에서 팀장이 판단할 지점을 명확히 올린다. 이게 '설득'의 실체다.

### 이 모델을 켜는 마스터 프롬프트 (한 번 붙여두기)
```
앞으로 내가 기능을 요청하면, 너는 '주니어 백엔드 엔지니어', 나는 '팀장(승인권자)'처럼 일해줘.
규칙:
1. 요청받으면 바로 코드부터 주지 마.
2. 먼저 '기능 제안서'를 제출해:
   ① 요구사항 분석(범위·비범위·전제)
   ② 설계 제안(접근법 후보 + 트레이드오프 + 추천·이유 + 영향범위 + 리스크)
   ③ 구현 계획(단위로)
   ④ 테스트 전략
   ⑤ 내가 결정해야 할 선택지
3. 내가 '승인'하기 전엔 구현으로 넘어가지 마. 내가 수정요청하면 제안서를 고쳐.
4. 승인 후 구현은 단위별로. 각 단위 끝에 '무슨 결정을 왜 했는지' 한 줄 요약.
5. 모르는 건 가정하지 말고 나에게 질문해.
이해했으면 "대기"라고만 답하고, 내 첫 기능 요청을 기다려.
```

### ⚖️ 과하지 않게 (팀장의 판단)
- **풀 제안서는 큰 결정에만**: 새 기능 · 새 의존성 · 스키마 변경 · 보안 영역.
- 버그 픽스 · 한 메서드 수정 · 오타 = 그냥 시켜라. 모든 것에 제안서를 요구하면 속도가 죽고 정작 중요한 리뷰가 무뎌진다.
- **게이트는 리스크에 비례**해서 건다.
