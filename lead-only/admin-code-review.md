# Admin 도메인 코드 리뷰 — 30년차 백엔드 관점 (Q&A)

> 학습 프로젝트로는 구조·계층·테스트·문서까지 잘 갖췄다. 아래는 **"실무(운영) 코드라면 짚었을 것"** 을 질문→답 형태로 정리한 것이다. 🔴=중요, 🟡=권장. 마감된 학습 프로젝트라면 당장 다 고칠 필요는 없고, "어디가 약한지 아는 것" 자체가 목적이다.

---

## A. 성능 · 확장성

### 🔴 A1. 목록을 `findAll()`로 전부 가져오는데, 회원이 수십만이면?
- **위치**: `AdminMemberService.getMembers()`, `getProducts()`, `getReports()`, `getComments()`
- **답**: 관리자 목록은 거의 항상 페이징이 전제다. `findAll()`은 테이블 전체를 메모리로 올려 지연·OOM을 부른다. `Pageable`을 받아 `Page<T>`로 반환하고, **정렬·필터(상태·기간)** 를 함께 설계해라. 관리자는 "정지된 회원만", "이번 주 신고만" 같은 필터를 반드시 원한다. 처음부터 페이징으로 짜는 게 표준이고, 데이터는 수천 건만 넘어도 체감된다.

### 🔴 A2. 목록 만들 때 `product.getMember().getId()`를 부르는데, 쿼리가 몇 번 나가나?
- **위치**: `AdminProductResponse.from()` → `product.getMember()`, `getCategory()` (LAZY 연관)
- **답**: 목록 루프에서 LAZY 연관을 건드리면 상품 N개당 추가 쿼리 N번 — **N+1 문제**다(상품 100개 = 쿼리 101번). 해결: ① `fetch join`/`@EntityGraph`로 한 번에 가져오거나, ② id만 필요하면 **DTO 프로젝션**(`select new ...`)으로 연관 로딩 자체를 피한다. 관리자 목록엔 ②가 깔끔하다. 진단은 `spring.jpa.show-sql=true` 켜고 쿼리 수를 세보면 즉시 보인다.

### 🟡 A3. 대시보드가 열릴 때마다 `count()`를 5번 도는데 괜찮나?
- **위치**: `AdminDashboardService.getDashboard()`
- **답**: 작을 땐 OK지만 `count(*)`는 큰 테이블에서 풀스캔이라 느려진다. ① 짧은 TTL 캐시(예: 30초)로 감싸거나, ② 조건부 집계로 쿼리 수를 줄이거나, ③ 트래픽이 크면 집계 테이블/카운터를 둔다. "관리 대시보드는 1초 단위 실시간 정확도가 필요 없다"는 점이 캐싱의 명분이다.

## B. 도메인 규칙 · 데이터 정합성

### 🔴 B1. 신고/회원 상태를 아무 값으로나 바꿀 수 있는데, 완료된 신고를 되돌리면?
- **위치**: `Report.changeStatus()`, `Member.changeStatus()` (검증 없이 `this.status = status`)
- **답**: 상태 전이 규칙(상태 머신)이 없다. 이런 불변식은 **admin 서비스가 아니라 엔티티(도메인)** 가 지켜야, 어디서 호출하든 안전하다. `COMPLETED`/`REJECTED`는 종료 상태라 변경 금지 같은 규칙을 엔티티 메서드 안에서 강제해라. 지금은 규칙이 코드 어디에도 없어 잘못된 전이가 그대로 통과한다.

### 🟡 B2. soft delete가 일관적인가?
- **위치**: 관리자 목록은 삭제건도 노출(`findAll`)하는데, 댓글 삭제는 `findByIdAndDeletedAtIsNull`로 막음
- **답**: "어디선 deletedAt을 필터하고 어디선 안 한다"가 섞이면 버그의 온상이다. 규칙을 한 곳에 정하고(예: 일반 조회 제외, 관리자만 포함) 팀 컨벤션으로 못 박아라. Hibernate 6의 `@SoftDelete`나 `@SQLRestriction`으로 강제하는 것도 방법. 또 관리자가 "이미 삭제된 댓글"을 지우면 404가 나는데, 이 UX가 의도된 건지도 정리해라.

### 🟡 B3. 두 관리자가 같은 회원을 동시에 수정하면?
- **위치**: 상태 변경 메서드 전반 (락 없음)
- **답**: 지금은 마지막에 저장한 사람이 이긴다(lost update). 관리자 동시작업이 드물면 용인할 수도 있으나, 중요한 엔티티엔 `@Version`(낙관적 락)으로 충돌을 감지하는 게 안전하다. "정지 처리가 조용히 덮어써지는" 사고를 막는다.

## C. 운영 · 보안

### 🔴 C1. 관리자가 회원을 정지/삭제했는데, **누가·언제** 했는지 어디 남나?
- **위치**: `changeMemberStatus()`, `changeReportStatus()`, `hideProduct()`, `deleteComment()` — 기록 코드 없음. 컨트롤러가 `@AuthenticationPrincipal`로 **행위자 admin id조차 안 받음**
- **답**: 안 남는다 — 관리자 기능의 가장 큰 구멍이다. 관리자 행위는 추적성(audit)이 필수다(분쟁·디버깅·규정). 최소한 **행위자·시각·대상·이전/이후 값**을 audit 테이블이나 구조화 로그로 남겨라. 구현은 AOP나 도메인 이벤트로 횡단 처리하면 비즈니스 코드를 안 더럽힌다. 먼저 컨트롤러가 acting admin을 받도록 고치는 것부터.

### 🔴 C2. 시드 관리자 비밀번호 `admin1234!`가 소스에 박혀 깃에 올라갔는데?
- **위치**: `AdminAccountInitializer`
- **답**: 자격증명이 VCS에 들어간 순간 유출로 본다. ① 비밀번호는 환경변수/시크릿으로 빼고, ② 운영에선 "알려진 비번 관리자"를 시드하지 말거나 최초 로그인 시 변경 강제, ③ 정 시드하려면 임의 비번 생성 후 안전 채널로 전달. 학습용이면 괜찮지만 "실무라면 사고"라는 감각을 가져라.

### 🟡 C3. 관리자 권한이 `ROLE_ADMIN` 하나뿐인데, 운영자/감사자/슈퍼관리자 구분이 생기면?
- **위치**: `SecurityConfig` `hasRole("ADMIN")` 단일
- **답**: 단일 역할은 곧 한계다. 읽기 전용 감사자와 정지·삭제 권한자를 같은 ROLE로 두면 위험하다. URL `hasRole`에서 **권한(authority) 기반 + 메서드 시큐리티(`@PreAuthorize`)** 로 진화할 여지를 열어둬라. 지금 당장은 아니어도 "권한 세분화 지점"을 인지하는 게 중요.

## D. 설계 · 유지보수

### 🟡 D1. 상태 변경마다 "String 받아서 try/catch valueOf"가 반복되던데?
- **위치**: `AdminMemberService.parseStatus()`, `AdminReportService.parseStatus()` (그리고 상품 TradeStatus)
- **답**: 같은 패턴 반복은 추상화 신호다. 또 하나, 지금은 `findById`(DB 조회) **후** 상태를 파싱해서 — 잘못된 입력인데도 DB를 먼저 친다. **검증을 DB 조회 앞으로** 옮겨라(불필요한 쿼리 절약 + 빠른 실패). 더 나아가 요청 DTO에서 enum으로 직접 바인딩하고 커스텀 처리로 깔끔한 400을 주는 방법도 있다.

### 🟡 D2. admin 서비스가 `member.changeStatus()`처럼 남의 도메인 엔티티를 직접 바꾸는데?
- **위치**: admin 서비스 전반의 변경 로직
- **답**: 읽기를 자체 Repository로 분리한 건 좋았다. 그러나 **변경**이 타 도메인 내부를 직접 건드리면, 그 도메인의 규칙·이벤트(예: 정지 시 알림 발송)를 우회하게 된다. 이상적으론 소유 도메인의 서비스(예: `MemberService.suspendByAdmin(...)`)를 통해 바꿔, 불변식이 한 곳에서 지켜지게 한다. 지금 구조의 트레이드오프를 인지해라.

### 🟡 D3. 테스트가 대부분 무거운 `@SpringBootTest`라 느리고, 공유 H2에서 시드 오염도 겪었지?
- **위치**: admin 컨트롤러 테스트 전반
- **답**: 통합 테스트는 몇 개의 스모크로 충분하고, 대부분은 슬라이스(`@WebMvcTest` 컨트롤러, `@DataJpaTest` 리포지토리)로 빠르게 가는 게 표준이다. 데이터 격리도 `@AfterEach deleteAll`보다 `@Transactional` 롤백이 깔끔할 때가 많다(겪은 카테고리 시드 오염이 그 증거). **테스트 피라미드**(단위 多 · 통합 少)를 의식해라.
